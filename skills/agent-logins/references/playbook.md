# Logins & CAPTCHAs — Playbook (detail behind SKILL.md)

## 1. Device-code OAuth (the `gh` pattern) — most reliable browser-free auth
Why it wins: no password typed anywhere, no token creation screens, token stored by the tool itself, no scheduled expiry with device flow.

Pattern for any CLI/service that offers it:
1. Agent starts the CLI login (`gh auth login`) and captures the one-time device code + URL (github.com/device).
2. User enters the code once on their phone (~30s). Agent polls/completes.
3. Afterwards everything is headless CLI/API. Record only account name + scope notes, never the token.

Generalizes: many CLIs (cloud providers, package registries, some SaaS CLIs) offer `--device` / "login in browser" flows built on OAuth device grants. Always check the CLI before automating a web login form. Anti-clickjacking note from the field: OAuth "Authorize" buttons may stay disabled for a few seconds — wait, don't force-enable repeatedly.

## 2. Assistant-owned mailbox + programmatic OTP — proven pattern
Assistant mailboxes are claimed via a human one-tap (claim session → confirmation tap), after which the mailbox is fully API-driven. One proven provider is mails.dev: configs live at `~/.mails/<name>.json` (mode 600) with keys: `api_key`, `mailbox`, `default_from`, `domain`, `mode`, `storage_provider`.

- List mail: `GET https://api.mails.dev/v1/inbox` with header `Authorization: Bearer <api_key>`.
- Read one: `GET https://api.mails.dev/v1/email?id=<id>`.
- Helper: `bin/mailbox_wait_code.py --config <name> --sender <substr> [--digits 6] [--timeout 120]` polls, extracts the code, prints one JSON line. The API key is never printed.

Rules: use each code exactly once and promptly (codes are single-use, short TTL); request at most one resend; snapshot the inbox's already-seen ids before triggering a send so a stale code isn't reused; if two codes are plausible, prefer the newest matching the current challenge.

Mailbox claim itself needs the human tap; plan for it instead of discovering it mid-signup. One mailbox per project/brand keeps account recovery paths separate.

## 3. Persisted browser sessions — log in once, reuse
- All browser tasks share ONE Chromium profile; run signup/login tasks SEQUENTIALLY (parallel tasks corrupt each other's session state). The persisted session is the access path — passwords are generated by the acting task and never reported.
- Same principle in raw Playwright: `chromium.launchPersistentContext(profileDir)` persists cookies/storage; delete the profile dir to force a fresh login.
- Session cookies are credentials: never export, log, or paste them into files or other tools.
- Google/social OAuth in automation: redirect-based flows reuse fine; popup-based "Sign in with Google" often blocks silently in headless contexts — switch to email-OTP flow (rung 2) or headed takeover instead of retrying the popup.
- Governed-fill designs exist (e.g. the agent drives, a vault fills, the agent never sees the password) — good reference architecture if the workspace ever needs credential fill beyond OTP.

## 4. CAPTCHA policy — the preference system
- Stored preference choices: `ask` (default), `solve`, `user_handles`; scope can be per-task or per-site. Read it before assuming; memory summaries cannot override the stored record.
- Only the user's own explicit statement saves a new choice ("solve CAPTCHAs for me on X" works; "make accounts overnight" / "you know what to do" do not — indirect wording gets rejected). Scope "this time" stays this time.
- If solving is authorized and attempts keep failing, stop and offer takeover — repeated challenge loops are themselves a bot signal.
- Legitimate, always-allowed moves: completing a challenge when `solve` covers it, user takeover, slowing down, switching flows (section 5). **Off-limits, do not recommend or use:** paid solving farms (2captcha/CapSolver-style), "stealth" evasion stacks (antidetect browsers, fingerprint spoofing, residential-proxy rotation), virtual/SMS-rental number mills. Beyond ToS violations, platform detection now profiles account+IP behavior server-side, so these convert recoverable friction into permanent bans and poisoned IPs — the opposite of capability.

## 5. Escalation & site lessons (field notes)
- **X:** Web signup forces phone ("Email signups are only allowed on the apps"). Datacenter IPs hit "temporarily limited your login" after a few attempts; credential-fill confirm steps have crashed sessions. Practitioner reports (2026): detection is behavioral at the API gateway (cookie entropy, device history); signup success tracks IP/email-domain reputation and improves after the profile "rests" a day or two. Rule: dedicated assistant account via official API or user takeover — never the user's personal account.
- **Kaggle:** reCAPTCHA sits on the email-register form; after account creation, GPU + notebook internet require phone verification (settings). Email-code step verified via mailbox API. Username availability must be probed — popular names are gone; prepare a fallback list before starting.
- **Reddit / dev.to:** reCAPTCHA before the form renders — budget a takeover step up front.
- **Hacker News:** account creation is trivial; the wall is downstream (Show HN blocked site-wide for new accounts). Create early, use later.
- **Generic signup walls** (defense-side literature, OWASP/industry): per-IP+per-account+per-fingerprint velocity limits, disposable-domain checks, cloud-IP scoring, progressive friction. Translation: come from a stable identity (same mailbox domain, same profile), at human cadence, once — not repeatedly.
- **"The account is the asset"** (practitioner maxim): per-thread locks, natural delays, rate limits — the win condition is never getting flagged, not getting through fastest.

## 6. Phone OTP
Only with the user's explicit authorization for that task. The number stays in local secure config only; it is passed solely into the current verification field and never printed, logged, or added to memory/chat. No number reachable → park as a human blocker with the exact prompt quoted. Never substitute rented/virtual numbers.
